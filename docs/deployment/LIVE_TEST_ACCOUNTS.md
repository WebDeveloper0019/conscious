# Live test accounts and disposable inboxes

These commands create **test accounts on the live database**, not real customer or seller identities. Run them over Hostinger SSH only after checking that `APP_ENV=production`, the migrations are current, and `PRIVATE_STORAGE_PATH` is outside the public web root.

1. `php private/ci-backend/backend/bin/create-test-mailboxes.php --confirm-live-test-mailboxes` creates 20 separate disposable inboxes through [Mail.tm](https://mail.tm/). The command can resume after rate limits or connection errors. It saves addresses, inbox passwords and mailbox IDs in `PRIVATE_STORAGE_PATH/test-accounts/mailboxes.json` with file mode `0600`. Mail.tm inboxes can expire or be removed; they must not become permanent customer or seller contact addresses. The provider has [API usage rules](https://docs.mail.tm/).
2. `php private/ci-backend/backend/bin/provision-live-test-accounts.php --confirm-live-test-accounts` creates 10 customers, 5 artisan vendors and 5 brand vendors. It requires all 20 inboxes, rejects existing matching accounts, and rolls back the whole database batch on failure. A second run refuses to overwrite accounts. The command writes a private CSV with each account's **site password** and **inbox password**. The CSV path is printed, but passwords are never printed.
3. Download the CSV through SCP to a restricted folder on the owner's computer. Open it in Excel if a sheet is needed. Never paste its contents into chat, email it as an unencrypted attachment, store it under `public_html`, or commit it to Git. Give each tester only their own row. Remove server and local copies when no longer needed.

The fictional names and store names are prefixed `Test` or `CI Test`. Customer accounts are active for login. Vendor accounts and applications are pending, with onboarding incomplete. No identity documents, bank/tax checks, products, orders, reviews, events, payments or approvals are fabricated. These vendors cannot sell until a real owner completes onboarding and an administrator reviews the submission.

The provisioner sets `email_verified=1` so the seeded accounts can sign in. That is an administrative test shortcut, **not proof that the application OTP flow was tested**. To check real email flows, request a password reset to one of the disposable inboxes and read the message through Mail.tm. Test registration OTP separately through the normal registration form. If mail is not delivered, stop and investigate the sending domain/provider before declaring email flows working.

Replace these records with genuine accounts through normal registration and review before handing them to real people. Do not simply rename fictional records or approve placeholder documentation. The placeholder `000000…` and `000001…` mobile numbers are for tests only and must never be used for SMS or delivery.
